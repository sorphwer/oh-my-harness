# Brainstorming

## Why

Implementation that skips intent capture tends to build the wrong thing well. A short brainstorm before planning or coding surfaces hidden constraints, rejected alternatives, and acceptance signals while changes are still cheap.

## Workflow

1. Restate the request in your own words and confirm.
2. Ask who the user is, what success looks like, and what would make the result wrong.
3. Surface constraints: data shape, permissions, existing patterns, deadlines, audience.
4. Sketch two or three concrete approaches with the main tradeoff for each.
5. Recommend one and name what would change your mind.
6. Stop. Do not start writing code or a plan until the user confirms direction.

## Output

A short shared understanding the user can correct in one message:

- Goal in one sentence
- Users and the success signal
- Constraints that matter
- Approach options and the recommended one
- Open questions, if any

## Avoid

- Do not jump to file lists, schemas, or code on the first turn.
- Do not present a single approach as if it were the only option when meaningful alternatives exist.
- Do not silently widen scope. Confirm before pulling in adjacent work.
