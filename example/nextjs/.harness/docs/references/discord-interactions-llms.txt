# Discord Interactions Webhook Reference — Discord Human Approval Desk
# This file is intended as context for LLMs assisting with Discord integration.

## Overview

This project uses Discord Interactions Webhook mode (not the Gateway/bot approach).
Discord POSTs interaction events directly to our endpoint: POST /api/discord/interactions.
No persistent bot process is required — fully compatible with serverless (Vercel).

## Setup Requirements

1. Create a Discord Application at https://discord.com/developers/applications
2. Set "Interactions Endpoint URL" to: https://<production-domain>/api/discord/interactions
3. Discord will send a PING to verify the endpoint (must respond with PONG)
4. Create a Bot user under the application
5. Store Bot Token in the workflow as an encrypted secret
6. Store Application ID in the workflow
7. Store Public Key in the workflow
8. Invite bot to server with permissions: Send Messages, Embed Links, Use Slash Commands

## Ed25519 Signature Verification

Every interaction POST includes:
- Header: X-Signature-Ed25519 (hex-encoded signature)
- Header: X-Signature-Timestamp (Unix timestamp string)
- Body: raw JSON body

Verification steps:
1. Parse the raw JSON only to identify the candidate Discord application
2. Load the matching workflow-scoped public key
3. Concatenate: timestamp + rawBody
4. Convert the workflow-stored public key from hex to Uint8Array
5. Convert signature from hex to Uint8Array
6. Use tweetnacl: nacl.sign.detached.verify(message, signature, publicKey)
7. If verification fails → return 401

IMPORTANT: Must read raw body (not parsed JSON) for signature verification.

## Interaction Types (incoming event type — NOT the same as Response Types below)

### Interaction Type 1: PING
- Discord sends this to verify endpoint
- Response: { "type": 1 } (PONG)

### Interaction Type 3: MESSAGE_COMPONENT (Button Click)
- Triggered when user clicks a button on a message
- data.custom_id contains our encoded action: "approve:<approval_request_id>" / "redo:<approval_request_id>" / "reject:<approval_request_id>"
- data.component_type: 2 (Button)

### Interaction Type 5: MODAL_SUBMIT
- Triggered when user submits a modal form
- data.custom_id: "redo_modal:<approval_request_id>"
- data.components[0].components[0].value: feedback text

NOTE: Interaction Type 5 (MODAL_SUBMIT) is NOT the same as Response Type 5
(DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE). These are different enums.

## Response Types

All response type values below are for the Interaction Callback Type enum
(not to be confused with Interaction Type which describes the incoming event).

### Type 1: PONG
```json
{ "type": 1 }
```

### Type 6: DEFERRED_UPDATE_MESSAGE (component-only, deferred update of original message)
Used for approve — silently acknowledges the interaction (no loading indicator), then
we update the original message later via webhook after executing the privileged API.
```json
{ "type": 6 }
```
Follow-up: PATCH https://discord.com/api/v10/webhooks/<app_id>/<interaction_token>/messages/@original

NOTE: Type 6 updates the ORIGINAL message (the one with buttons). This is different from
Type 5 (DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE) which creates a NEW "loading" message.
Type 6 is the correct choice for component interactions where we want to modify the
existing message.

### Type 7: UPDATE_MESSAGE (component-only, immediate update of original message)
Used for reject and redo modal submit — immediately updates the original message content
and components in place.
```json
{
  "type": 7,
  "data": {
    "content": "Request rejected by username",
    "components": []
  }
}
```

NOTE: Type 7 updates the ORIGINAL message in place. This is different from Type 4
(CHANNEL_MESSAGE_WITH_SOURCE) which creates a NEW message. Empty components array
removes all buttons from the original message.

### Type 9: MODAL
Used when user clicks Redo — opens a modal with text input.
```json
{
  "type": 9,
  "data": {
    "custom_id": "redo_modal:<approval_request_id>",
    "title": "Provide Feedback",
    "components": [{
      "type": 1,
      "components": [{
        "type": 4,
        "custom_id": "feedback",
        "label": "Feedback",
        "style": 2,
        "required": true,
        "placeholder": "Explain what should be changed..."
      }]
    }]
  }
}
```

### Summary: Response Type Selection

| Action              | Interaction Type     | Response Type | Rationale                                    |
|---------------------|----------------------|---------------|----------------------------------------------|
| PING                | PING (1)             | PONG (1)      | Endpoint validation                          |
| Approve (button)    | MESSAGE_COMPONENT (3)| Type 6        | Defer, execute API, then PATCH original msg  |
| Reject (button)     | MESSAGE_COMPONENT (3)| Type 7        | Immediate update of original message         |
| Redo (button)       | MESSAGE_COMPONENT (3)| Type 9        | Open feedback modal                          |
| Redo (modal submit) | MODAL_SUBMIT (5)     | Type 7        | Immediate update of original message         |

### Types NOT used (and why)

- Type 4 (CHANNEL_MESSAGE_WITH_SOURCE): Creates a NEW message. Not suitable because we
  want to update the existing button message, not create a separate reply.
- Type 5 (DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE): Creates a NEW "loading" message. Same
  issue — we want to update the original message, not create a new one.

## Sending Messages (Bot Token)

To send the initial approval message with buttons:
POST https://discord.com/api/v10/channels/<channel_id>/messages
Authorization: Bot <DISCORD_BOT_TOKEN>

```json
{
  "content": "New approval request: ...",
  "components": [{
    "type": 1,
    "components": [
      { "type": 2, "style": 3, "label": "Approve", "custom_id": "approve:<approval_request_id>" },
      { "type": 2, "style": 1, "label": "Redo", "custom_id": "redo:<approval_request_id>" },
      { "type": 2, "style": 4, "label": "Reject", "custom_id": "reject:<approval_request_id>" }
    ]
  }]
}
```

Button styles: 1=Primary (blurple), 2=Secondary (gray), 3=Success (green), 4=Danger (red)

## Editing Messages

### Via Interaction Token (preferred for interaction responses)
After responding with Type 6 (DEFERRED_UPDATE_MESSAGE), update the original message:
PATCH https://discord.com/api/v10/webhooks/<app_id>/<interaction_token>/messages/@original
No Authorization header needed — the interaction token in the URL is the auth.

@original refers to different messages depending on the response type:
- After Type 5: @original = the new "loading" message that was created
- After Type 6: @original = the original message the component was attached to

### Via Bot Token (for editing messages outside of interaction context)
PATCH https://discord.com/api/v10/channels/<channel_id>/messages/<message_id>
Authorization: Bot <DISCORD_BOT_TOKEN>

## Key Constraints

- Must respond to interactions within 3 seconds (use deferred response for slow operations)
- Interaction tokens expire after 15 minutes
- Raw body must be preserved for signature verification (do not parse then re-stringify)
- Bot must have permissions in the target channel
- Discord credentials are workflow-scoped, not platform-wide environment variables

## Packages
- tweetnacl: Ed25519 signature verification (nacl.sign.detached.verify)
- No discord.js or discord-interactions library needed for webhook mode
